# 自开发闭环设计（Orchestrator 改 Orchestrator）

> 目标：让 Orchestrator 自己完成一次真实的代码改动——出纲领 → 改文件 → **跑验证** →
> **读报错继续改** → 直到客观验收通过 →（可选）**重新打包并重启**，全过程可审计、可回滚、可人工接管。

## 一、为什么不能直接上"自开发"

历史运行数据（48 份纲领 / 182 步，真实任务 15 次）显示：

- 真实任务只有 5 次真正 `done`；"让它改自己"的几次恰好是最失败的（`failed` / `cancelled`）；
- 纲领里的依赖是线性的（74% 的步骤声明依赖上一步），并行执行的理论收益只有 1.0x；
- 执行段目前**只能写文件、不能跑任何验证**，所以它写完不知道对不对，也没法自己修。

结论：自开发的瓶颈不是"能不能并行"，而是**能不能闭环**——缺的是"跑命令"和"按报错再改"。

## 三、P1/P2 设计要点

### 命令从哪里来

执行段已经在 `StepOutput.commands` 里给"建议命令"。语义升级为：

- 命令**命中白名单**且用户开启了命令执行 → 系统真的跑它，并把输出回给模型；
- 否则保持旧行为：只展示，不执行。

### 安全边界（缺一不可）

1. **白名单前缀匹配**：`command_allowlist` 里逐行写允许的前缀（如 `python -m pytest`、`ruff`）。
2. **不经过 shell**：命令拆成参数列表执行，`|`、`&`、`>`、`%VAR%` 等一律拒绝。
3. **只在工作区内执行**：`cwd` 固定为当前运行的工作区（`Workspace.root`），不接受绝对路径切换。
4. **超时 + 输出截断**：默认 120 秒；输出保留头 2000 + 尾 2000 字符（报错通常在尾部）。
5. **默认关闭**：`allow_command_execution` 默认 `false`，开启是用户的显式动作。

### 迭代闭环

```
执行段产出文件改动
   → 落地 + 备份 + diff（已有）
   → 跑白名单内的命令
      → 全部通过：进入客观验收
      → 有失败且还有轮次：把「命令 + 退出码 + 报错尾部」回灌给执行段，让它继续修
      → 轮次用尽仍失败：该步 blocked，报错摊开给用户（不许标 done）
```

### 验收标准（可自检）

- 白名单外的命令**永不执行**（单测：注入 `rm -rf` / `&&` 链式命令必须被拒）；
- 命令只在工作区内跑（单测：cwd 越界/绝对路径被拒）；
- 失败命令的输出能回到执行段上下文（单测：第二轮请求里能看到失败输出）；
- 命令失败且轮次用尽时，步骤是 `blocked` 而不是 `done`；
- `command_allowlist` 为空时行为与旧版本完全一致。

## 四、P4 打包重启的设计约束（先记下来，避免后面踩坑）

- **不能自杀**：正在运行的 exe 文件被锁，打包必须先结束进程。所以重启请求交给外部辅助脚本
  （保存运行记录 → 等端口释放 → 重新打包 → 拉起新实例），主进程只负责落盘后退出。
- **重启后要能接上**：复用 `recover_interrupted()`，把中断的运行收敛成 `paused`，用户点「继续执行」即可。
- **可回滚**：改自己之前先做 git 快照（提交到分支或打 stash 点），失败可一键回到改动前。

## 五、非目标

- 不做并行执行（数据表明当前收益 ≈ 1.0x，等纲领能表达并行结构再说）；
- 不做任意命令执行（只跑白名单；`rm`、`git push` 这类永不自动跑）；
- 不改变"人工确认门"——纲领仍需用户确认后才执行。
