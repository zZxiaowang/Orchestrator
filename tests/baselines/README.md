# 回归基线（Baseline）

本目录记录**第 1 步冻结时的回归基线**，用于判断后续任何一步是否破坏了既有能力。

## 基线数字

| 套件 | 命令 | 基线（第 1 步冻结） |
| --- | --- | --- |
| 后端 pytest | `python -m pytest -q` | 69 项全部通过 |
| 界面自检 | `node scripts/ui_check.mjs` | 25 项全部通过（真实鼠标 / 键盘 / 滚轮） |

判定规则：**用例数只能增加、不能减少**。数量变化必须在提交说明里写明新增 / 删除原因；
删除既有用例属破坏性变更，需先在 `docs/next-phase-architecture.md` 第 7 节登记。

> 首次落地时请在本机实跑一次确认上表数字；若与 69 / 25 不一致，以实跑结果为准更新本表。

## 怎么跑

```bash
# 后端（在仓库根目录）
python -m pytest -q

# 界面自检（需要本地服务可启动，参数见 scripts/ui_check.mjs 头部说明）
node scripts/ui_check.mjs
```

Windows 下可先用 `start-demo.cmd` 拉起演示环境，再跑界面自检。

## 跑之前的基本检查

1. 工作区为全新空目录时，不要让架构段产出“盘点现有代码”这类需要既有代码的步骤（见 `docs/state-and-event-contracts.md` 第 4 节）。
2. 涉及界面的改动必须先跑 `node scripts/ui_check.mjs`，重点看三栏布局滚动与设置弹窗可点性（历史上被 `display:grid` 覆盖 `hidden` 破坏过）。
3. 涉及 `resp.aread()` 的错误路径，确认错误信息已完成 bytes→str 归一。

## 基线漂移怎么处理

1. 先判断是本步**有意**新增能力导致的，还是回归。
2. 回归 → 修代码，不改测试断言。
3. 有意新增 → 更新上表数字，并在提交说明里列出新增用例清单。
4. 任何情况下都不允许把失败用例改成 skip 或删除来“过基线”。

## 与后续步骤的关系

- P0（步骤 2–6）：基线应 ≥ 69 / 25，并新增指标、降级、质量门相关用例。
- P1（步骤 7–10）：新增命令生命周期、检索、续聊用例；命令相关用例必须覆盖三类否定路径——未确认不执行、越界拒绝、非白名单拒绝。
- P2（步骤 11–13）：新增队列持久化与恢复用例；托盘能力必须验证“缺少依赖时程序仍可启动”。
